# Crypto Monitor 反向需求文档

更新时间：2026-04-23

## 1. 文档目标

本文档基于当前代码实现反向抽取业务需求，用于回答三个问题：

1. 这个项目现在实际上在做什么。
2. 这个项目产品化后应该满足哪些核心需求。
3. 后续迭代时，哪些需求应该优先补齐。

当前代码分析范围主要覆盖：

- `crypto_monitor/main.py`
- `crypto_monitor/monitor.py`
- `crypto_monitor/market.py`
- `crypto_monitor/ai_service.py`
- `crypto_monitor/notifier.py`
- `crypto_monitor/storage.py`
- `crypto_monitor/config.py`
- `crypto_monitor/models.py`

## 2. 产品定位

### 2.1 产品一句话定义

一个面向 Web3 交易者的实时监控与告警系统，将行情波动、链上事件和 AI 解读转化为可执行的通知。

### 2.2 当前代码体现出的产品定位

从现有实现看，项目当前是一个以 Solana Meme 币/主流币为主的轻量监控机器人，具备：

- 多币种价格轮询
- 波动阈值判断
- AI 短评生成
- Telegram 通知
- SQLite 状态持久化
- 简单 HTTP 健康检查服务

### 2.3 目标用户

- 高频关注币价波动的个人交易者
- 关注钱包异动、代币热度、流动性变化的 Web3 用户
- 想把监控能力作为社群/VIP 服务输出的运营者

## 3. 产品目标

### 3.1 核心目标

1. 及时发现市场异动。
2. 降低用户盯盘成本。
3. 将“数据”转成“可读、可执行”的告警。
4. 提供稳定的 7x24 小时运行能力。

### 3.2 现阶段目标

1. 稳定监控一组配置好的代币。
2. 对超阈值波动生成 AI 解读并通知。
3. 支持服务重启后的状态恢复。
4. 暴露基础状态接口，便于部署与运维。

## 4. 现有功能反向拆解

### 4.1 已具备功能

1. CLI 启动和运维命令
   - 启动监控
   - 单次执行
   - 测试连接
   - 查看状态
   - 添加/移除监控币种

2. 行情监控
   - 从代理网关抓取交易对价格
   - 计算相邻采样点涨跌幅
   - 按 `minor/moderate/major` 三级阈值分类

3. AI 洞察
   - 按模板拼接提示词
   - 生成结构化短评
   - 对非 JSON 输出做兜底解析

4. 通知能力
   - Telegram 异步发送
   - 限流
   - 健康检查通知

5. 存储能力
   - 价格历史
   - 告警历史
   - 币种状态恢复
   - 监控名单持久化

6. 服务接口
   - `/`
   - `/health`
   - `/status`

### 4.2 已暴露但尚未完全产品化的能力

1. 健康检查配置存在，但运维动作仍偏轻量。
2. 监控名单可持久化，但没有用户配置界面。
3. AI 洞察结构化了，但未形成报告/复盘产品。
4. HTTP 服务存在，但更像运维接口，不是业务 API。

## 5. 用户故事

### 5.1 交易者视角

1. 作为交易者，我希望在币种波动超过阈值时收到即时告警。
2. 作为交易者，我希望告警里不只有涨跌数字，还能有一句简短解读。
3. 作为交易者，我希望同一波行情不要重复轰炸我。

### 5.2 运维者视角

1. 作为运维者，我希望服务有健康检查接口，便于容器探活。
2. 作为运维者，我希望程序失败后能自恢复，而不是静默停掉。
3. 作为运维者，我希望重启后还能保留监控名单和上一轮状态。

### 5.3 产品运营视角

1. 作为运营者，我希望后续把监控能力扩展到链上钱包、鲸鱼地址、DEX 交易和社交情绪。
2. 作为运营者，我希望未来能形成日报、周报和高价值事件复盘。

## 6. 功能需求

## 6.1 基础监控需求

1. 系统应支持配置多个监控币种。
2. 系统应支持按固定间隔抓取行情。
3. 系统应支持基于涨跌幅阈值触发告警。
4. 系统应支持同一币种的冷却时间。

## 6.2 AI 解读需求

1. 系统应支持为告警生成 50 字以内的短评。
2. AI 输出应包含最少以下字段：
   - `comment`
   - `sentiment`
   - `risk_hint`
3. 当 AI 输出异常时，系统应自动降级为默认评论。

## 6.3 通知需求

1. 系统应支持 Telegram 通知。
2. 系统应支持每分钟总量限流。
3. 系统应支持单币种最小发送间隔。
4. 系统应支持健康检查消息发送。

## 6.4 存储需求

1. 系统应保存价格历史。
2. 系统应保存告警历史。
3. 系统应保存币种最后价格和最后告警时间。
4. 系统应保存监控名单。

## 6.5 运维需求

1. 系统应提供 HTTP 健康检查接口。
2. 系统应提供状态查询接口。
3. 系统应支持 graceful shutdown。
4. 系统应支持日志输出和日志滚动。

## 7. 非功能需求

### 7.1 性能

1. 单轮检查应在监控间隔内完成。
2. 市场抓取和通知不应阻塞主循环。
3. 存储写入应尽量批量化。

### 7.2 稳定性

1. 外部请求失败时应支持重试。
2. 连续失败达到阈值时应触发健康检查逻辑。
3. 服务重启后应尽量恢复运行前状态。

### 7.3 可扩展性

1. 应允许未来扩展更多链和更多数据源。
2. 应允许未来增加更多通知渠道。
3. 应允许未来将 AI 能力从“短评”扩展到“事件分析”。

## 8. 当前版本未覆盖但业务上应补齐的需求

1. 链上钱包/巨鲸/合约事件监控
2. DEX 交易、流动性池和新币上线监控
3. 社交媒体与情绪数据融合
4. 多维策略规则引擎
5. 多租户与用户自定义监控
6. Web 控制台和配置中心
7. 日报/周报/复盘报告
8. 历史回放与回测能力

## 9. 成功指标建议

1. 告警端到端延迟
   - 目标：从事件发生到通知送达尽量控制在秒级

2. 告警准确率
   - 目标：减少噪音告警和重复告警

3. 服务稳定性
   - 目标：核心服务长时间稳定运行

4. 用户价值
   - 目标：告警打开率、点击率、复盘使用率逐步提升

## 10. 建议的需求演进阶段

### Phase 1：稳定监控机器人

- 稳定价格监控
- 稳定告警
- 稳定恢复

### Phase 2：多源实时监控系统

- DEX 数据
- 链上钱包异动
- 多通知渠道
- 更强规则引擎

### Phase 3：产品化监控平台

- 用户配置中心
- 多租户
- 报告与复盘
- 策略回测
- 订阅与商业化能力
